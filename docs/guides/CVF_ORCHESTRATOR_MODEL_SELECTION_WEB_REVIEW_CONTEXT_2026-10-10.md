## Current Design Projection

The Non coder gives the outcome, budget, rights, and other meaningful constraints;
technical model choice is handled by the orchestrator when the operator assigns or
delegates that choice. The operator controls topology and may explicitly assign a
model, delegate choice for a task, or grant a bounded standing choice authority.
Choice never grants invocation. The orchestrator cannot select or replace its own
active seat through this capability.

The first surface is **AGENT_SEAT**: a worker in an operator-started IDE/agent
session. The existing task, work order, dispatch and delegation owners admit the
seat and hold its manual selection rationale. A Model Gateway registry entry,
health check or GatewayReceipt is not a prerequisite. Manual declarations do not
intercept hidden host changes. **GATEWAY_API** is a later, separate surface requiring
its actual policy, registry, capability, health and receipt owners; its companion
needs fresh implementation authority.

Selection uses a task acceptance floor and distinct checks for choice authority,
seat or API admission, data/context policy, methods/tools, version-specific quality,
and budget. Only eligible configurations enter cost comparison. Record provider,
model ID/alias, immutable snapshot if exposed, effort, harness/version/settings,
tool profile, role and evidence window, with explicit unknowns. Published model
cards, technical reports and original benchmark methods are prior evidence;
separate them from reviewed task outcomes. Alias-only identity is at most partial
applicability. A new version does not inherit an old score automatically.

**Explicit operator assignment with missing quality evidence:** if the assigned
model is available and no hard conflict is known, SELECT it and record
`HONORED_WITH_EVIDENCE_GAP`, the missing evidence/confidence limit and mandatory
independent acceptance against the unchanged task floor. Quality may remain
`INSUFFICIENT`; SELECT does not assert quality or authorize invocation. HOLD an
assignment for unavailability, authority/policy/method/context conflict, a known
failed hard requirement, or an existing task/budget/effect admission failure.

**Delegated choice with insufficient or absent quality evidence:** HOLD_EVIDENCE
or choose another adequately supported eligible candidate. `PROVISIONAL` choice
requires positive relevant evidence and a bounded local task: read-only or
reversible documents/pure implementation, no protected-control, auth, credential,
external or production effects, adequate tools, observable independent acceptance
and admitted budgets. Higher risk goes to the existing authority owner. No model
choice authority yields a recommendation only. An empty candidate set holds;
multiple eligible candidates are allowed, with exactly one selected.

Cost comparison concerns total *accepted delivery*: orchestration, preparation,
execution, review, repair and failure burden. Monetary estimates, measured bills,
subscription allocation, quota/rate/time windows and token usage have different
units and evidence. Unknown cost remains unknown; a quota-only cap can be assessed
without a monetary estimate, while a hard monetary cap needs supported bounds.
The six related historical worker observations are not a comparative model trial:
their model identity was operator-reported, bills were unavailable, and task,
effort and harness effects were confounded. No fixed model-to-task ranking follows.

## Logical Contract And Chain

The proposed logical records are TaskProfile, CandidateConfiguration,
VersionEvidence, SelectionDecision, ReviewedOutcomeLink and
LearningConsumptionLink. They are sections/joins in existing governed task evidence,
not six databases or a deployed schema. The first manual AGENT_SEAT selection is
recorded in the work order. A future task's existing independent review owns the
single outcome record. The historical six-row ledger stays read-only.

```text
outcome + authority -> task/acceptance profile -> eligible seat configurations
-> version/method evidence -> frozen manual decision -> separately admitted dispatch
-> actual return + independent review -> outcome disposition
-> zero/one/many later decisions citing applicable evidence or control
```

The proposed decision is frozen before dispatch with task, configuration, evidence
and authority pins. Material drift creates a successor decision; no silent fallback
or retry beyond the existing grant. States `DRAFT`, `FROZEN`,
`BOUND_TO_DISPATCH`, `OUTCOME_LINKED`, `LEARNING_DISPOSITIONED` describe selection
record progress only. Append transitions rather than editing frozen bytes.
`LEARNING_DISPOSITIONED` may mean there is no reusable lesson and does not claim
later application. Later decisions own their own links. Typed parent-control
DELIVERY/APPLICATION evidence belongs to the existing Project Learning Loop;
ordinary local performance observations use cited/action-verified/reasoned-no-change
evidence and are not automatically parent controls.

The planned order is design review, one admitted real manual task, a later task
that tests learning consumption, optional strict schema only if manual use shows
value, then optional runtime automation under separate authority. There is no
arbitrary benchmark quota or automatic phase activation. Expense is parked.
